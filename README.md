# ir-agent V0 — 事实账本与确定性计算层

投研 Agent 的地基。这一层不含任何 LLM：它的唯一职责是保证**数字是对的、时点是对的、每个数字都能反查到原始接口响应**。

V1 起才把正文撰写交给分析师 Agent，但占位符契约不变——因此那时模型依然**物理上无法编造数字**。

## 快速开始

```bash
python -m ir_agent 600519 --year 2025
```

退出码 0 表示通过验收门槛（三表勾稽无失败 + 数字可溯源率 100%）。

```bash
python -m pytest -q -m "not live"    # 离线，约 1.3s
python -m pytest -q                  # 含真实网络请求，约 25s
```

批量跑一组标的：

```bash
./runall.sh                     # 跑 universe.txt，年度 2025
./runall.sh 2024                # 换年度
./runall.sh 2025 my_list.txt    # 换样本文件
```

`universe.txt` 每行三列（代码 行业 名称），`#` 开头为注释。单份完整输出落在
`runs/<年度>/<代码>.txt`，便于事后翻查告警细节。30 家约 3–4 分钟。

**不要去掉 `ir_agent` 内部的限流 sleep** —— 东财有 IP 频控。

输出里三个信号需要关注：

| 信号 | 含义 |
|---|---|
| `⚠ 本期分歧` | 两源在本期数字上不一致，结论可能有问题 |
| `✗ 因抓取不全` | **故障**。写着「正常跳过」的那些不用管 |
| 退出码 | `0` 通过 · `1` 未过门槛 · `2` 运行失败 |

## 架构

```
巨潮公告 ──→ 披露日 (as_of)
                 │
新浪三表 ────────┴──→ 事实账本 ──→ 确定性算子 ──→ 占位符草稿
腾讯行情 ────────┘                                    │
                                                 渲染 + 审计
```

| 模块 | 职责 |
|---|---|
| `ledger.py` | `Fact` / `FactLedger`，`as_of` 时点守卫，修订版本管理 |
| `citation.py` | 占位符 `[[source#key@period]]` 解析、脚注、裸数字审计 |
| `sources/snapshot.py` | 原始响应落盘，内容寻址 |
| `sources/cninfo.py` | 巨潮公告（**披露日的唯一来源**），orgId 查询 |
| `sources/financials.py` | 三表 Tier-1：新浪，逐表溯源 |
| `sources/eastmoney.py` | 三表 Tier-2：东财，自带公告日 |
| `sources/quotes.py` | 行情 Tier-1 腾讯 / Tier-2 新浪 |
| `sources/resolve.py` | 多源降级 + 交叉验证 |
| `operators/` | 增长率、利润率、杜邦、倍数、DCF |
| `validate/reconcile.py` | 三表勾稽 5 项 |
| `validate/adjudicate.py` | 用年报原文裁定两源分歧 |
| `sources/annual_pdf.py` | 年报 PDF 提取（合并资产负债表） |
| `audit.py` | 验收审计 |
| `pipeline.py` | 端到端编排 |

## 五条不可妥协的设计约束

**1. 数字一律 `Decimal`。** `Fact` 构造时拒绝 `float`。财务计算里浮点误差不是理论风险。

**2. 取值必须过 `as_of`。** `ledger.get(key, period, as_of=...)` 只返回该时点已披露的最新版本；请求尚未披露的事实抛 `LookAheadError`。`ledger.pin(date)` 可固定时点，让调用方不可能忘记传。

**3. 财报的 `as_of` 来自巨潮公告日，不是抓取日，也不是报表日期。**
新浪财报里没有披露日，所以 `to_facts` 强制要求外部传入 `as_of_by_period`；没有披露日的期间**直接丢弃而非猜测**。用抓取日代替披露日会让回测凭空多出几天信息优势，而且不会报错——这是本项目最重视的一类 bug。

**4. LLM 只写占位符。** 正文写 `[[sina_profit_xxx#revenue@2025FY]]`，渲染阶段由代码填真值并生成脚注。`audit_bare_numbers` 会拦截任何未经账本的裸数字。

**5. 缺数据时「跳过」而非「通过」。** `ReconcileReport` 把 `ok`（已跑的都过了）与 `complete`（覆盖完整）分开暴露。静默通过会让一份数据残缺的报表看起来完全健康。

## 数据源分层

| 数据 | Tier-1 | Tier-2 | 覆盖差异 |
|---|---|---|---|
| 三表 | **东财 datacenter**（规范化） | 新浪财报 | 东财字段名跨行业一致、自带 `NOTICE_DATE`、覆盖金融业模板 |
| 行情 | 腾讯 qt.gtimg | 新浪 hq.sinajs | **新浪无市值/PE/PB**，降级后估值章节会缺失 |
| 公告 | 巨潮 cninfo | — | 单一权威源，无替代 |

降级只解决「拿不到数据」；**交叉验证解决「拿到了错的数据」——后者更危险，因为它不会报错。**
两源都可用时逐字段比对，Tier-1 的值仍然胜出（保证有可用数字），但分歧记录在案。

分歧按期间分诊：**期外分歧**（常见于追溯调整）是情报，**本期分歧**才影响结论。
两者混在一起会让告警很快被无视。`--strict` 只在本期分歧时判失败。

### 为什么东财是 Tier-1

字段映射错位属于**静默出错**，东财反爬失败属于**大声失败** —— 后者有降级、重试
和跨源勾稽兜得住，前者只能靠人事后发现。所以主干押在规范化接口上，
把解析路径完全独立的新浪留作 Tier-2，交叉验证价值不变。

### 规范化接口 vs 文本标签匹配

这是 L0 层最重要的一个结构性选择。

**新浪**按**文本行标签**返回，而标签写法因行业、因发行人而异：

| 概念 | 制造业 | 银行 | 保险 |
|---|---|---|---|
| 所有者权益合计 | `所有者权益(或股东权益)合计` | `股东权益合计` | `所有者权益合计` |
| 归母净利润 | `归属于母公司所有者的净利润` | `归属于母公司的净利润` | `归属于母公司股东的净利润` |
| 营业收入 | `营业收入` | `营业收入` | `一、营业收入` |

只能靠「剥前缀 → 别名表 → 形状正则」三层去追，而且**每遇到一类新发行人就会再漏一次**。

**东财 F10 是规范化接口**：按行业提供四套模板（通用 `G` / 银行 `B` / 保险 `I` / 证券 `S`），
而**四套模板的字段名完全一致** —— `TOTAL_ASSETS`、`NETPROFIT`、`PARENT_NETPROFIT`
在哪套里都是同一个名字。换行业只换模板名，映射表一个字不用改。

`detect_company_type()` 依次试探四套模板并缓存结果。接入后东财对银行/保险/证券的
勾稽覆盖从 **1/5 提升到 4/5**，跨源验证由「覆盖不足」恢复为「一致通过」。

唯一的真实差异是 `OPERATE_COST` 只存在于通用模板 —— 金融业确实没有营业成本，
这是业务差异不是映射缺口。

### 接口声称的公告日未必对应它给的数字

**这是 V0 最重要的一个发现，也推翻了我选 Tier-1 的部分理由。**

中国神华 2025FY，东财给 `total_assets = 903,830 百万` 并标注
`NOTICE_DATE = 2026-03-31`。但 2026-03-31 发布的年报原文写的是 **627,761 百万**
（第 148 页合并资产负债表，新浪与之完全一致）。

东财供的是**重述后**的数字，却挂上了**原始公告日** —— 等于在数据源层面
内建了未来函数：它声称 903,830 在 2026-03-31 可知，而当天的年报根本不是这个数。

我把东财提为 Tier-1，理由之一恰恰是「它自带 NOTICE_DATE」。**这条理由现在不成立了。**

对策不是换回 Tier-2（东财在字段规范化与金融业覆盖上仍然更强），而是加一层裁决:

    本期出现分歧 → 从巨潮定位该年度年报 → 提取合并资产负债表 → 判定谁与原文一致

裁定后**采用胜出源的原始事实**（`method` 仍为 `REPORTED`，溯源仍指向接口快照），
PDF 只当裁判，裁定过程另行记录。`--strict` 只拦**未裁定**的分歧。

Tier 顺序解决「默认信谁」，裁决解决「这一次谁对」—— 两者不能互相替代。

### 年报 PDF 的上下文隔离

`fetch_and_extract()` 只返回结构化结果，PDF 全文（神华 2025 年报 310 页、5.8MB）
始终留在函数内部。V1 的影子 Agent 会沿用同一契约 —— 它替换的是
「怎么在 PDF 里找到那一页」，而不是「谁持有全文」。

年报只在**真的出现分歧时**才下载，并按快照目录缓存。

### 分歧的形状指向不同病因

两源分歧不能一概而论，**形状**是最有效的分诊信号:

| 形状 | 特征 | 病因 | 处理 |
|---|---|---|---|
| `annual_only` | 只在 FY 期间分歧，中期逐项一致 | 年报**追溯重述** | 回公告原文裁定 |
| `all_periods` | 所有期间都分歧 | **字段映射错误** | 先查适配器 |
| `mixed` | 两者都不像 | 不确定 | **不给标签，交人工** |

`all_periods` 由中国国航实测得到（`cash_net_change` 全期为 0，补充资料行覆盖主表行）。

中国神华是 `mixed`：分歧横跨 2024FY / 2025FY / 2025H1，资产类在 Q1、Q1-Q3 一致
但 H1 的收入与现金项不一致。**只看 `total_assets` 一个字段会误判成 `annual_only`** ——
这也是分类器该拒绝给标签的原因：证据不足时沉默好过一个自信的错误结论。

### 交易所识别用白名单，不用 else 兜底

早期是 `"SH" if code.startswith(("60","68")) else "SZ"` —— 一个 `else` 兜住了所有
非沪代码，**北交所（43/83/87 段）会被静默当成深市**，拿到一份空数据却不报错。
实测东财 F10 与新浪财报**均不覆盖北交所**（新浪只返回 `19700101` 占位列），
因此 `market_of()` 对北交所明确抛错，拒绝用错误后缀去取空数据。

### cninfo orgId 必须查询，不能推导

贵州茅台的 orgId 是 `gssh0600519`，隆基绿能是 `9900022338`——**格式不统一**。
早期版本用 `f"gssh0{code}"` 推导，在茅台上碰巧成立，在隆基上直接返回 0 条公告、整条链路断掉。
`lookup_org_id()` 走 cninfo 的 topSearch 接口并缓存。

## 口径说明

**新浪财报是累计口径。** `20250930` 列是前三季度累计，不是 Q3 单季。因此 `period_label` 把它标为 `2025Q1-Q3` 而非 `2025Q3`——防止有人拿它当单季做同比。

**「净利润」在两张表都出现**，分别映射为 `net_profit`（利润表）与 `cf_net_profit`（现金流量表），否则跨表勾稽会变成自己跟自己比。

## 三表勾稽的 5 项

| 校验 | 状态 |
|---|---|
| 资产 = 负债 + 所有者权益 | ✓ |
| 净利润 = 归母 + 少数股东损益 | ✓ |
| 期末现金 = 期初 + 净增加额 | ✓ |
| 利润表净利润 = 现金流量表起点 | ✓ |
| 毛利 = 营业收入 − 营业成本 | 通常 skip |

最后一项在 CAS 利润表中无「毛利」行，因此常态跳过。这是正确行为——若把 `gross_profit` 合成出来再校验，这条就成了恒真式。覆盖率显示为 4/5 是诚实的，不是缺陷。

## 已知限制

### V0 范围内、尚未完成

- **DCF 算子写好但未接入流水线。** `operators/dcf.py` 有 3 个函数、4 个测试，
  但 `pipeline.py` 从不调用它 —— 研报里不出现 DCF 估值。接入需要先定
  增长率与折现率的假设来源（这本身是个方法论决定，不只是接线）。
- **行情两源都是 HTTP 网页接口。** 位置分隔的非官方格式（已加字段自洽校验与
  停牌检测兜底）。主干仍应换 `mootdx`（通达信协议），走 TCP 不触发反爬。
- **无并发。** 重试已有（`sources/retry.py`，指数退避），但全流程串行，
  30 家约 3–4 分钟。并发会撞上东财频控，需要先设计限流策略。
- **公告解析只覆盖合并资产负债表。** `annual_pdf.py` 目前只提取资产负债表
  用于裁决，利润表与现金流量表未做。
- **无行业对比。** 只做单公司，可比公司分析未实现。

### 数据边界（不是缺陷，是现实）

- **北交所无财报数据源。** 东财 F10 与新浪均不覆盖，`market_of()` 明确抛错。
- **一致预期不可得。** 免费源无可靠覆盖，影响「预期差」类分析。
- **北向资金已停止披露。** 2024-08 起无每日净买入数据，不应接入。

### 交给 V1

- 研报正文由分析师 Agent 撰写（当前是模板拼接，无洞察）
- 多空辩论与风控对抗
- 影子 Agent 处理长文档（`annual_pdf.py` 已确立上下文隔离契约）
- 决策日志与事后反思

## 测试

347 个测试，其中 17 个命中真实网络（标记 `live`）。全部按 TDD 写就：先写失败的测试，再实现。

开发过程中被测试抓到的十五个真实缺陷：
1. 时点守卫拦下了「用当日行情做历史时点分析」——暴露出流水线需要对行情类事实优雅降级并显式记录跳过。
2. 派生事实的 `source_id` 含 `::` 与 `@`，占位符正则解析不了，导致 `[[...]]` 原样留在成稿里。
3. 三表事实全部指向资产负债表的快照——审计能通过，但反查会查到错的文件。**指错文件的溯源比没有溯源更危险，因为它看起来是通过的。**
4. cninfo 的 orgId 用 `f"gssh0{code}"` 推导，在茅台上碰巧成立，换到隆基绿能就返回 0 条公告。**只用单一标的验证的数据适配器，等于没有验证。**
5. 定期报告标题正则过窄：五粮液用「一季度报告」而非「第一季度报告」，且季报存在「（更新前）/（更新后）」后缀，`$` 锚点全部漏匹配 —— 该标的只识别出 3 个期间（应为 8 个）。
6. 公告分页在 `max_pages × page_size` 处静默截断。温氏股份正好 300 条命中上限，2024 年报被切掉，同比随之缺失 —— **「我们没抓到」伪装成了「数据不存在」**。
7. 行情事实的 period 语义错配: `market_cap` 被挂在 `2025FY` 上，实际是当日快照。已改用报价日（`2026-09-04`）作即期期间，PB/PE 明确表达为「即期市值 ÷ 财报期分母」。
8. **报表行标签跨行业写法不同。** 保险用「一、营业收入」、银行用「股东权益合计」、平安用「归属于母公司股东的净利润」—— 精确匹配在跨行业时大面积失配。已改为「规范化剥前缀 → 别名表 → 形状正则」三层匹配。
9. **`_compose` 与算子调用都没有分段容错。** 银行没有营业成本，一个字段缺失让整轮以裸 `KeyError` 收场。已改为逐段独立 try。
10. **粗粒度分段会让不适用的字段带走关键结论。** 毛利率与杜邦原本同段，导致银行的 ROE 一并丢失 —— 而 ROE 恰是银行最核心的指标。
11. **低覆盖的源「通过」是虚假安慰。** 东财对银行只能跑 1/5 项校验却显示「一致通过」。已加覆盖门槛，不达标的源标注「覆盖不足，不计入佐证」，且交叉验证失效时**必须显示**（藏起来等于谎称验证过）。
12. **新浪现金流量表有两行都映射到 `cash_net_change`**：主表行「五、现金及现金等价物净增加额」与补充资料（间接法）行「现金及现金等价物的净增加额」。我此前把后者当作异写加成别名，实为**语义不同的另一行**；中国国航补充资料未填（0）且排在后面，last-write-wins 让 0 覆盖了 −67.4 亿，勾稽随之失败。茅台两行值相同所以完全看不出来 —— **这类 bug 只有跨源独立勾稽能抓到**。已改为首个命中获胜。
13. 交易所识别用 `else` 兜底，北交所被静默当成深市（见上）。已改白名单。
