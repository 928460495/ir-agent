# 因子的「检索词」字段（B3 扩展）

## 一、为什么 B3 的第一版不够

B3 第一版（commit `370c441`、`a7dca3d`，已落地）加了 `_core_candidates`：
按特指度降序出候选词，L1 整串标签 → L2 去括号的头 → L3 头剥后缀。它靠
**括号这个结构信号**切分，对带括号注解的标签有效。

实测它的覆盖边界，发现一类同样常见、而它完全处理不了的形状——**不带括号
但同样冗长的标签**：

| 标签 | `_core_candidates` 产出 | 会出现在年报里吗 |
|---|---|---|
| `服务器及通信用高端覆铜板出货量同比增速` | `[整串, 服务器及通信用高端覆铜板出货量同比]` | 不会（17 字） |
| `前五大客户销售收入占营业收入比重变化率` | `[整串, 前五大客户销售收入占营业收入比重]` | 不会（15 字） |
| `单位产品电力及蒸汽能耗成本贡献` | `[整串, 单位产品电力及蒸汽能耗成本]` | 不会（13 字） |

这类标签里**没有任何结构信号**告诉代码该从哪儿切。要处理它得知道
「服务器及通信用」是修饰语、「高端覆铜板」是对象、「出货量」是度量——
那是语义分析，不是字符串操作。

顺带发现的小缺口：`_SUFFIXES` 里有「增速」没有「同比增速」，所以上表第一行
剥出来的尾巴上挂着一个没剥干净的「同比」。

**唯一知道该用什么词去检索的，是生成这个标签的那个模型。** 所以这一版
给它一条显式通道。

## 二、`Factor.search_term`，以及让它可信的那道闸门

`Factor` 加第五个字段：

```python
search_term: str = ""   # 用什么词去找（必须是 label 的子串）
```

**闸门：非空时必须是 `label` 的子串，且 ≥2 字。** 违反则抛
`DecompositionInvalid`。

### 为什么是「子串」

这条约束把性质变了：**模型只能指认自己标签里的一段，不能凭空提供新词汇。**
这正是本仓库「代码观测 > 模型声称」那条原则的应用——不是完整核验，但它给
捏造划了边界。

没有这道闸门，模型可以给「产能」这种泛词，而它在一家覆铜板公司的年报里
到处都是；那一次巧合命中会被标成「年报披露」、进入 DCF 因子的依据链。
实测数据：「服务器」在真实公告语料（8 篇，89055 字）里出现 **18 次**、
「覆铜板」98 次。**代价不对称站在闸门这一边。**

### 括号内的词可以当检索词——这是一处**刻意的不对称**

实测验出：`铜箔` 是 `原材料成本(铜箔/电子级玻纤布/环氧树脂价格)` 的子串，
所以子串闸门**放行**模型把括号内的词当检索词。而 B3 第一版的 spec 花了
整节论证「`_core_candidates` 绝不下探括号内」。

**这不是矛盾，是刻意的不对称，决定已做出：允许。**

理由在于被禁的是什么。B3 第一版禁的是**代码**盲目下探——代码分不开
`铜箔`（覆铜板的原材料，真信号，命中 6 次）与 `通信`（下游行业名，巧合，
命中 4 次），它只能按长度或位置排，而实测已证明长度分不开。**模型分得开**：
它知道哪个词是度量、哪个是下游行业名、哪个是材料。

收益是具体的：`产能利用率(稼动率同比变化)` 的最佳检索词是**「稼动率」**，
它在年报里真实存在、且比「产能利用率」更可能逐字出现——而它在括号里。
改成「去括号后的头的子串」会把它一起挡掉。

**残留风险，不粉饰**：模型若给 `覆铜板下游需求规模(服务器/…)` 配上
`服务器`，闸门拦不住，那 18 次巧合命中会被标成「年报披露」。缓解只有四条，
没有一条是硬闸门：

1. 提示词说明检索词是干什么用的（第六节）
2. 状态标签本身写着「文字依据，是否给出具体数值待人工确认」
3. `_valid_hit` 的否定语境判断仍然逐候选词生效
4. 它在 **L4 最底端**——只有 L1–L3 全部落空才会被试

**谁要「修平」这处不对称，请先读这一段。** 往任一方向修都会破坏一个已做
出的决定：让代码下探括号内，会重新引入「把巧合伪装成证据」；禁止模型指认
括号内，会丢掉「稼动率」这类最优词。

### 这条约束损失了什么，明确记下来

`前五大客户销售收入占营业收入比重变化率` 的最佳检索词也许是
「客户集中度」——它在年报里真的会出现，而且比任何子串都准。但它**不是**
标签的子串，所以本设计不接受它。

这是一笔明知的交易：**用一部分召回，换「新通道不可被凭空滥用」。**

### 闸门装在 `Factor.__post_init__`，不装在解析处

`Factor` 是 `@dataclass(frozen=True)`，`__post_init__` 里抛异常可行（frozen
只禁赋值）。装在这里的理由是本仓库自己的判例——`assume.py:1098` 那段注释
记着一次真实事故：

> 生益科技目录里残留的 9/14 那份 `assumptions.json`，营收链里还有
> 「高端产品收入占比」——新闸门在预研时会拒收它，**读回时却能一路走进
> 建模**。与「人手改 JSON 可能引入重复行」同一类：**不依赖上游一定
> 已经查过。**

`Factor` 有三条构造路径（DSL 解析、`assume._decomp_from_dict` 的 JSON 读回、
测试），装在构造函数里一次性覆盖全部，没有「哪几条路记得加闸门」这个问题。
这与仓库已有的做法同形：`Tier.COMPANY` 的字节码不变式、`_PREFIX` 的枚举
测试——**让错的事做不成或变响，而不是靠记得去查。**

一个事实要说清，但它不改变上面的决定：`gaps.collect` **只在第一阶段被调用**
（`full.py:1490`，`run_valuation` 不调它），所以一个坏检索词读回到第二阶段
**今天**不会被用于匹配。但「今天成立」正是本仓库反复被咬的那类断言，不作为
省掉闸门的理由。

## 三、三条构造路径上的错误转译

`__post_init__` 抛的是 `DecompositionInvalid`，而现有的两处
`except DecompositionInvalid` 都只包着 `check_closure`/`check_dimensions`
这类**构造之后**的调用，**不包构造本身**。所以三条路各自要把它翻译成本层
的错误：

| 构造点 | 现状 | 本设计要求 |
|---|---|---|
| `methodology.py:79` 的 `Factor(...)` | 不在任何 try 内 | 包起来 → `MethodologyFailed`，**走既有重试通道**（`max_attempts=3`，驳回原因会喂回模型，见 `methodology.py:227-239`） |
| `assume.py:154` 的 `Factor(...)`（经 `from_json`） | `full.py:1741` 的调用点**完全没兜**，抛出会直接崩掉第二阶段命令 | 在 `from_json` 外包一层 → `SystemExit`，措辞照 `assume.py:1109` 的「请重跑第一阶段，重新预研分解式后再填判断项」 |
| 测试里的 `Factor(...)` | — | 不需要转译 |

第二行要强调：`run_valuation` 对 `AssumeFailed` 的捕获在 `full.py:1809`，
**在 `from_json`（1741）之后**，所以那里抛任何异常都会崩。而 `full.py:1733`
与 `:1743` 本来就在用 `raise SystemExit("…")` 处理「这份文件不可用，请做 X」，
照那个形状办即可。

## 四、DSL 与往返

格式从 `名称:单位:线索` 变成 `名称:单位:线索:检索词`。

**向后兼容是免费的**：解析处现在是

```python
label, unit = bits[0], bits[1]
hint = bits[2] if len(bits) > 2 else ""
```

第 4 段**今天被静默丢弃**，所以旧的 3 段文件自然得到空检索词、退回
`_core_candidates` 的前三级。

要改的四处，缺任何一处检索词都会在某条路上被静默丢掉：

1. `methodology.parse`（`:76` 附近）—— 取 `bits[3]`
2. `methodology._to_dsl`（`:259`）—— 写出 4 段。**不改这里，人工编辑
   `drivers.md` 后重跑会把检索词吃掉**，而那个往返是写进文件末尾的承诺
3. `methodology.to_markdown`（人读表）—— 加一列「检索词」
4. `assume._decomp_to_dict`（`:147`）与 `_decomp_from_dict`（`:155`）——
   两边都带上。后者用 `f.get("search_term", "")`，与既有的
   `f.get("source_hint", "")` 同形

### 冒号碰撞：这道闸门顺手挡住一个今天潜伏的 bug

`raw.split(":")` 对所有字段生效。若 `source_hint` 里出现冒号，一行 3 段的
因子会被切成 4 段，尾巴落进检索词位。

**而 hint 的片段几乎不可能是 label 的子串**——于是子串闸门把它拦下并说出
原因，而不是让一个 hint 碎片悄悄变成检索词。今天这个碎片是被 `bits[2]`
之后静默丢弃的，看不见；加了第 4 段之后它会变成一个假检索词，而闸门正好
挡住这个新风险。

## 五、检索词在候选阶梯的**最底端**

```
L1 整串标签 → L2 去括号的头 → L3 头剥后缀 → L4 模型给的检索词
```

**不是顶端。** 「出货量」比整串标签更泛，不是更具体；放顶端会压过更具体的
候选，颠倒「按特指度排序」这条原则。检索词存在的理由恰恰是**前三级全部
落空**，所以它只在最后被试——这也是保守方向。

签名变化：

- `_core_candidates(label: str, search_term: str = "") -> list[str]`
- `_match_annual(sections, label, search_term="")`
- `_match_report(corpus, label, search_term="")`
- `_match_announce(corpus, label, search_term="")`
- `collect` 三处调用传 `f.search_term`

全部带默认值，所以既有调用与既有测试不受影响。2 字下限对 L4 同样生效
（闸门已经保证 ≥2，这里是纵深）。

## 六、提示词

在 `methodology.py` 的 DSL 说明处（`:181-182` 附近，和「闭合的硬性要求」
并列）加一条，**连理由一起写**——这个仓库的提示词都写为什么，不只写规则：

> 每个因子再给一个**检索词**：年报/公告里会**逐字出现**的那个词，且
> **必须是因子名里的一段**。
>
> 因子名可以写完整（「服务器及通信用高端覆铜板出货量同比增速」），但那样的
> 整串不会出现在任何年报里——检索词才是代码真正拿去全文搜索的东西。
>
> 不能另造词：「客户集中度」即便更准，只要不在因子名里就会被驳回。

同时更新文件末尾那段往返说明（`methodology.py:289`）的语法示例。

## 七、代价，明确记下来

**① 方法论环节多了一个失败模式。** 这是第一次因为「一个可选字段写得不对」
而驳回。模型容易改对（只是一个字段，且驳回原因会喂回去），但 3 次驳回
失败 = `MethodologyFailed` = `meth = None` = **整个因子层消失**。这个代价
要在它第一次发生之前就写明，而不是等实跑时才发现。

**② 「待人工确认」的面会继续扩大。** 与 B3 第一版同一条：L4 让更多因子拿到
`年报披露`/`公告披露`/`研报测算`，而这三个状态的含义都是「文字依据，是否
给出具体数值待人工确认」。

**③ 它把子项目 B 终审 Important #1 的地盘再扩大一次。** `assume.py:952` 的
闸门对任何非 `MISSING` 状态硬驳回「无数据（估计）」。若实跑中因此反复被
驳回，该动的是闸门或那条出口，**不是回头把 L4 拿掉**。

## 八、测试

**闸门的双向断言是核心**：

```python
def test_检索词必须是标签的子串():
    Factor(key="k", label="服务器及通信用高端覆铜板出货量同比增速",
           unit="变化率", search_term="出货量")          # 子串，通过
    with pytest.raises(DecompositionInvalid):
        Factor(key="k", label="前五大客户销售收入占营业收入比重变化率",
               unit="变化率", search_term="客户集中度")   # 非子串，拒收
```

第二条断言钉的是第二节那笔明知的交易。它会红，意味着有人放宽了闸门——
那是一个要重新讨论的决定，不是一次「改进」。

**那处刻意的不对称也要双向钉住**，否则下一个人会把它当不一致修平：

```python
def test_代码不下探括号内而模型可以指认():
    # 代码侧：B3 第一版的决定，不得倒退
    assert "铜箔" not in _core_candidates("原材料成本(铜箔/电子级玻纤布/环氧树脂价格)")
    # 模型侧：括号内的词可以当检索词，闸门放行
    f = Factor(key="k", label="产能利用率(稼动率同比变化)",
               unit="变化率", search_term="稼动率")
    assert f.search_term == "稼动率"
```

两条断言在同一个测试里，因为它们是**同一个决定的两面**。分开写，将来
只会有一半被读到。

其余：

- 空检索词通过（向后兼容），1 字检索词拒收（下限）
- **L4 在最底端**：构造一份语料，让 L2（去括号的头）与 L4（检索词）
  都能命中、且在不同容器里，断言采用的是 **L2**。把 L4 挪到顶端会红。
- L4 兜底生效：前三级全部落空、只有检索词能命中时，命中
- **三条构造路径的错误转译各一条**：
  - `methodology.parse` 遇到非子串检索词 → `MethodologyFailed`（**不是**
    `DecompositionInvalid` 漏出去），且消息里带因子名与那个检索词
  - `from_json` 遇到非子串 → `SystemExit`，消息含「请重跑第一阶段」
  - `Factor(...)` 直接构造 → `DecompositionInvalid`
- **四处往返各一条**，缺一处就会静默丢字段：
  - `parse` 读到第 4 段
  - `_to_dsl` 写出第 4 段，且 `parse(_to_dsl(m))` 的检索词与原值相等
  - `to_markdown` 的表里出现检索词
  - `_decomp_to_dict` → `_decomp_from_dict` 往返后检索词不变
- 冒号碰撞：`名称:单位:年报附注:汇兑损益:xxx` 这类 hint 带冒号的行，
  第 4 段不是 label 子串 → 被闸门拦下并报错，**不是**静默变成检索词
- 既有回归：B3 第一版那 10 条测试、`_core_label` 那 7 条、
  `_valid_hit` 的 4 条否定语境测试，全部继续绿

## 九、不做什么

- **不做 `_SUFFIXES` 的补全**（「同比增速」没剥干净那个小缺口）。它是独立
  的一件事，而且加了检索词之后，L4 比多剥一个后缀更能解决问题。
- **不放宽子串闸门**（第二节已论证，并有反向断言守）。
- **不「修平」代码与模型在括号内这件事上的不对称**（第二节已论证，并有
  双向断言守）。它是刻意的：代码分不开 `铜箔` 与 `通信`，模型分得开。
- **不把检索词放到阶梯顶端**（第五节已论证，并有测试守）。
- **不做 `PDF_MAX_PAGES = 30` 截断 235 页年报**、**不做 ②.5 的槽位浪费**
  —— B3 第一版的 spec 已把这两件划出范围，仍然在范围外。
- **不改 `_core_label`、`_valid_hit`、`_SUFFIXES`、`_PAREN`**。
- **不引入任何新的第三方依赖。**
