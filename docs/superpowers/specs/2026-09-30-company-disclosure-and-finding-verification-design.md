# 公司披露入语料库 + Finding 引文的代码核验（子项目 B）

> 缘起：子项目 A 落地后，`2026-09-20-openweb-corpus-design.md` 第二节把
> 子项目 B 定为「因子搜索面扩大 + 把 `Finding` 从『模型说它在这个网址见过』
> 升级成『代码确认这句话在这个网址上』」。真实运行的数据把这个框法改掉了
> 一半——见第一节。用户另外提出把公司官方信息纳入采集范围。

## 一、实跑推翻了「扩大搜索面」这个框法

2026-09-30 对 600183 跑完第一阶段（`out/600183-ow4`），8 个分解式因子的
实际状态：

| 因子 | 状态 | 实际发生了什么 |
|---|---|---|
| 良率 | 研报测算 | ③ 命中东吴证券研报，只有文字没有数值 |
| 名义产能 | 无数据 | **搜到了**，单一媒体（港湾商业观察） |
| 产能利用率 | 无数据 | **搜到了**，全是财经媒体 |
| ASP | 无数据 | 同上 |
| 提价传导幅度 | 无数据 | 同上 |
| 产品结构升级 | 无数据 | **搜到了**，单一媒体（腾讯新闻） |
| 稼动率摊薄固定成本 | 无数据 | 同上，全是财经媒体 |
| 原材料成本冲击 | 无数据 | 真的什么都没搜到（8 个里只有这 1 个） |

**7 个「无数据」里 6 个其实搜到了东西**，被 `web.supports_value` 以「来源
等级不够」挡下。只有 1 个是真的搜不到。

所以瓶颈不是**搜得不够广**——搜得更广只会搜到更多财经媒体。同一轮里开放
网络采集的 10 篇文档也曾 10/10 落 MEDIA（A 的第一次实跑），是同一个根因。

由此本子项目分成两件独立的事，各自解决一半：

- **往阶梯里加一个高等级的确定性来源**（公司公告），而不是设法让模型搜得
  更好。理由与本项目「代码观测 > 模型声称」一致：模型挑什么网址不可核验，
  一个确定性接口可核验。
- **把 `Finding` 的证明力真正建立起来**（B2），从而让「等级」这个代理指标
  不必再承担它承担不了的职责。见第五节。

### 公告能覆盖多少：如实说

公告是**公司级事实**的权威来源，不是**行业级数据**的来源。逐个对上面 8 个
因子：扩产/投产公告能给「名义产能」，年报与公告的高端占比能给「产品结构
升级」，提价公告可能给到「ASP」「提价传导幅度」的公司侧口径；而「产能
利用率」「良率」A 股基本不披露（`gaps.py` 模块注释早已记下这一点），
「原材料成本冲击」「稼动率摊薄固定成本」属上游价格与内部核算，公告不会给。

乐观估计覆盖 3/8。**不把本子项目写成「解决了瓶颈」**：它把「七个因子无
数据」挪到「四五个因子无数据」，剩下那几个属于 A 股确实不披露——那种情况下
「标为估计、绝不用代理指标顶替」本来就是 `gaps` 的正确行为，不是待修的缺陷。

## 二、`Tier.COMPANY`：第四级，以及它唯一的安全支点

`external.py` 的 `Tier` 新增第四个成员，`TIER_LABEL` 与 `TIER_RULE` 同步。
规则照 SELLSIDE 的形状写——公司披露的两面性与卖方研报同构：

    COMPANY   上市公司法定披露 —— 公告中的**事实**（产能、投产、订单、
              股权变动、提价）可直接引为依据；**管理层对前景的表述不得
              作为本报告任何假设的依据**。

「事实 vs 管理层展望」的区分**写在 `TIER_RULE` 里、不加代码闸门**，与
SELLSIDE 现有做法一致（研报里的事实可引、预测不可引，靠提示词约束）。
代码分不出一句话是事实还是展望，硬加闸门只会误杀。

### 唯一的安全支点

**`Tier.COMPANY` 只能由巨潮适配器赋予，绝不加进 `web.tier_of(publisher)`
的白名单。**

`tier_of` 吃的是**模型自报的机构名字符串**。一旦把公司名加进它的白名单，
模型在 `发现:` 行里写一个 `| 生益科技 |` 就能把任意网页拔到 COMPANY 级
——而 COMPANY 够格支撑因子取值（第五节），那等于一句转述直接决定 DCF 里
的一个数。

这与子项目 A 里 `tier_of_url` 和 `tier_of` 必须并存、不能合并是同一条理由：
**同一个 Tier 值，由代码赋予和由模型声称，安全性差一个量级。** 分级跟着
来源的**取回方式**走，不跟着名字走。

`openweb.tier_of_url` 也不动——公司自有 IR 站点不映射为 COMPANY。公告只
从巨潮这一条确定性路径进来。

## 三、公告采集：模型挑标题，代码抓正文

新建 `ir_agent/sources/announce.py`。

```
cninfo.search(code, as_of−12个月, as_of)      代码，确定性接口
      ↓  只把「序号 + 标题 + 披露日」交给模型
模型挑出与本次分解式相关的若干条，上限 8 篇
      ↓  代码按 ann_id 去巨潮下载 PDF
PyMuPDF 取文（既有依赖，annual_pdf.py / annual_sections.py 已在用）
      ↓
Document(tier=COMPANY, prompt_limit=2000) → corpus.add_if_visible
```

**模型给的是指向代码已有列表的下标，不是 URL。** 它编不出一条不存在的
公告；正文的下载地址来自巨潮的接口响应，不来自模型。可编造的空间从「任意
网址」缩到「这些条目里的哪几条」——这个契约比 openweb 的 discover/fetch
分工**更强**，那里模型给的还是一个它可以凭空构造的 URL。

最坏情况是模型挑了一条不相关的公告，代价是浪费提示词长度，**不是把假证据
放进语料库**。

**时点守卫按 `Announcement.ann_date`（披露日）**，不是抓取日。`cninfo.py`
模块注释已经记下这条：把抓取日当 as_of 会让回测凭空多出几天信息优势，且
不会报错。

规模：12 个月窗口、上限 8 篇、进提示词截 2000 字、入库存全文（与 openweb
的截断口径一致，理由见 `Document.prompt_limit` 的字段注释）。

## 四、`gaps` 阶梯插进 ②.5

```
①账本 → ②年报叙述章节 → ②.5 公司公告 → ③研报语料库 → ④开放网络
```

公告排在研报之前：它是公司权威披露、且由确定性接口取回，比两级模型中介的
来源更近。命中时状态标签用**「公告披露」**，不能沿用「研报测算」——那会把
一份公司公告说成券商测算，是错误归因。

与 ② 一致，②.5 命中只标「文字依据，是否给出具体数值待人工确认」并交出
原文片段与出处：**命中关键词不等于拿到了数值**，这是 `gaps` 模块注释里
写死的一条。

## 五、B2：`Finding` 引文的代码核验

`web.search` 返回 `Finding` 之后，对每条用 `openweb.fetch` 把网址抓回来，
核验模型转述的 `claim` 是否真的出现在正文里。

| 核验结果 | 处置 |
|---|---|
| 通过 | 算合格来源。入库的 `Document.text` 用**代码抓回的全文**替换原来的 `x.claim`；`tier` 按 `tier_of_url(最终域名)` 重判 |
| 抓不到（超时/403/PDF/正文为空） | **降级为线索**：不算进 `supports_value`，清单注明「模型转述未能在原页核实」 |
| 抓到了但原文里没有这句话 | 同上 |

按用户决定，**每条 Finding 都发一次 HTTP 请求**（不按等级预筛）。不调模型，
只是网络时间，且抓不到不阻断。

### 顺带补掉一个活着的洞

`gaps.collect` 在 ④ 通过时把 `Finding` 包成 `Document` 放进语料库，
`text=x.claim`——**那是模型转述的一句话，从没被抓取过**，`tier` 来自
`web.tier_of(模型自报的机构名)`。它和代码亲手抓回来的文档躺在同一个
`Corpus` 里，`Corpus.verify()` 分不出来。

子项目 A 的终审把这条记为 NEW-3 并判「本轮不可达」（那次实跑 ④ 一条都没
通过）。它是活的。B2 落地后这条路径上的 `Document` 携带的是代码抓回的全文，
与 openweb 文档同质。

## 六、`supports_value` 的门槛，以及它与 B2 的耦合

改为：

| 情形 | 结果 |
|---|---|
| 有任何**通过 B2 核验**的 finding | 够格 |
| 只有降级为线索的 finding | 不够格 |
| 一条 finding 都没有 | 不够格 |

即 MEDIA 不再一票否决。「优先级放在最后」落成两件事：`findings` 按 tier
降序排列（媒体排末尾）；**仅靠媒体支撑的因子在批准清单上明确标注**「仅
财经媒体支撑（已在原页核实）」，让人在批准时看得见证据强度。

### 这个放宽为什么安全，以及它依赖什么

**MEDIA 门槛今天存在的理由，恰好是 B2 要消除的那个东西。**

`supports_value` 的注释写的是「一条财经媒体报道可以作为线索，不该单独决定
DCF 里的产能增速」。但真正危险的不是「媒体」这个等级——是那条
`Finding.claim` **是模型转述、代码从没核实过**。等级只是不可核验性的一个
代理指标。

B2 之后，每条合格 finding 的 claim 都被代码在原页上核实过。「媒体 + 已
核实」与「媒体 + 未核实」不是同一个东西。

**因此这个放宽只在 B2 同轮落地时成立。** 这是一条硬依赖：将来若有人把
B2 拆走、只保留放宽，门槛就成了裸的——那时一句只在财经媒体上出现过、且
无人核实过的转述可以直接进 DCF。**不要把第六节和第五节分开实施。**

### 一处有意保留的不一致

③ 研报语料库的命中**仍然跳过 `Tier.MEDIA` 文档**（子项目 A 的终审 C3 加的
闸门），而 ④ 放宽了。这不是遗漏：

- ③ 是**关键词命中**。`gaps` 自己的注释写着「命中关键词不等于拿到了数值」
  ——年报里出现「稼动率」三个字，可能只是一句「稼动率保持稳定」。
- ④ 是**定向搜到的具体数据点，且经 B2 在原页逐字核实**。

**同一个 Tier，证明力不同。** 谁要「修正」这处不一致，请先读这一段。

## 七、错误处理（全部不阻断）

| 情形 | 处置 |
|---|---|
| `cninfo.search` 失败 | 不入公告，清单记「公司公告采集未执行（原因）」；其余照常 |
| 模型挑标题这步失败 | 同上 |
| 某篇公告 PDF 下载失败 / PyMuPDF 取文为空 | 该篇不入库，清单记失败篇数与原因（与 `openweb.fetch_failed_reasons` 同一口径） |
| 公告披露日晚于 as_of | `add_if_visible` 记入 `skipped` |
| B2 核验失败 | 该 finding 降级为线索，不阻断该因子的其余 finding |
| 全部 finding 都降级 | 该因子落「无数据」，清单说明是「核实不通过」而非「没搜到」——两者对读者含义不同 |

一条都不阻断整轮研究。资料收集的失败最坏后果是「这个因子缺证据」，不是
「整轮分析作废」。

## 八、测试

- 新增 `Tier.COMPANY` 后，三个提示词拼装点自动打印其 `TIER_RULE`
  （它们已按 `for t in Tier` 遍历）
- **不变式：`web.tier_of` 的任何白名单都不得产出 `Tier.COMPANY`**——这是
  第二节那条安全支点的守卫
- 公告：模型挑出的下标越界/重复/挑了不存在的序号 → 忽略该项，其余照常
- 公告：披露日晚于 as_of → 被挡下并计入 `skipped`
- 公告：PDF 取文为空 → 该篇不入库、计数，其余照常
- ②.5 命中 → 状态标签是「公告披露」，不是「研报测算」
- B2：claim 在原页 → 合格，且入库 `text` 是抓回的全文（不是 `claim`）
- B2：claim 不在原页 → 降级为线索，不算进 `supports_value`
- B2：抓取抛 `FetchFailed` → 同上，且不牵连同因子的其余 finding
- `supports_value`：全媒体但都通过核验 → 够格；全媒体且都降级 → 不够格
- `supports_value`：`findings` 按 tier 降序，媒体在末尾
- 仅媒体支撑的因子 → 批准清单出现「仅财经媒体支撑」标注
- ③ 仍跳过 MEDIA（第六节那处有意的不一致不被"修正"掉）

## 九、不做什么

- **不做电话会议纪要/投资者关系记录**。

  我自己验过的（可复核）：巨潮公告库拿不到。`cninfo.search` 对 600183 取回
  近 21 个月 220 条公告，其中 6 条命中「说明会」的全是「关于召开…业绩说明会
  的公告」——**只是召开通知，没有纪要正文**；对深市 300782 / 000333 / 002049
  取回 304 / 301 / 374 条，**零条**「投资者关系活动记录表」；带
  `searchkey=投资者关系活动记录` 跨 `column=szse|sse` 与两个 `category`
  共六种组合，`totalAnnouncement` 全为 0。所以它不在公告库里，而在按交易所
  分裂的两个独立平台上。

  一次专门的可行性探查（**结论未经我独立复核**，我的抽查因用错查询参数而
  无效）报称：深交所互动易 `irm.cninfo.com.cn` 可返回真实问答正文与时间戳、
  零新依赖，但结构性只覆盖深市——5 个沪市代码（含 600183）全部 `total=0`；
  上证e互动 `sns.sseinfo.com` 对沪市可用，但 600183 在其上几乎没有内容
  （仅 1 条未回答的提问）；上证路演中心未找到 JSON 接口，仍是假设。

  结论：**沪市（含当前标的 600183）当前拿不到纪要。** 按本仓库对 Plan 4 与
  少数股东市值法的既有处置——标记为阻塞于数据源缺失，不用只有元数据的替代源
  去凑（那会破坏逐字引文的不变量）。深市适配器是一个干净的后续项目，但**开工
  前应先独立复核上面那三条报称的结论**：它们决定的是「做不做」，而不是
  「怎么做」。
- **不做 B3（③ 研报语料库命中率）**。语料库现有 16 篇而 ③ 只命中 1/8，
  `_core_label` + `_valid_hit` 的关键词匹配确实弱，但那是独立的一件事。
- **不改 `basis.validate` / `external.attribute` 的分级接受度**。子项目 A
  的终审两轮都指出它们对任何分级一视同仁地放行 EXTERNAL 引文；用户已决定
  警告不驳回（`Corpus.media_cited` 机制），本轮不重开这个决定。
- **不把「事实 vs 管理层展望」做成代码闸门**（第二节已论证）。
- **不引入任何新的第三方依赖**。`cninfo`、`requests`、PyMuPDF 都是既有的。
